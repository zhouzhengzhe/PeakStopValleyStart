# dsh-peak-valley-brake

[English](README.md) | 中文

一个 DeepSeek Harness 插件：在 API 处于峰时计价期间停止发出请求，谷时计价恢复后自动复工，并且**绝不丢失**被它扣下的工作。

## 它解决的问题

DeepSeek 按时刻计费（[官方定价页](https://api-docs.deepseek.com/quick_start/pricing) 脚注 3）：

| | 时段（UTC） | 时段（UTC+8） |
|---|---|---|
| **峰时** | `01:00–04:00`、`06:00–10:00`，周一至周五 | `09:00–12:00`、`14:00–18:00`，工作日 |
| **谷时** | 其余全部时间，含周六周日全天 | 其余全部时间 |

谷价是峰价的一半。一个跑着编码任务的 agent 若横穿峰时窗口，窗口内每一次请求都付双倍。

## 它做什么

在**步骤边界**——唯一一个"agent 已启动的工具全部跑完、且尚未为任何新请求付费"的时刻——刹车拒绝进入下一步。谷时计价恢复后，它把扣下的工作放回收件箱并唤醒 agent。不拦截时它完全透明：不改写消息、不注入任何内容、不改变请求前缀。

```
谷时                武装（峰前 5 分钟）   峰时（UTC 01:00–04:00）   放行（峰末 + 1 分钟）
   │                      │                    │                        │
   │  步骤自由进入         │  步骤被拒          │  步骤被拒              │  扣下的工作
   │                      │  工作被记账        │                        │  重新投递
```

### 为什么是"拒绝"而不是"取消"

循环在步骤的模型请求**之后**才执行该步骤的工具。因此步骤边界是唯一一个"没有东西正在半途"的位置：调用 `agent.cancel` 会腰斩一个正在写文件的工具。本插件**从不调用** `cancel`。

### 一个天真的刹车会销毁你的提示词

这是整个设计所依赖的、唯一一个不显然的事实，已在 `@deepseek-ai/dsh-agent-loop` 中核实：

```js
const claimed = this.inbox.claim(target, position.turn);       // 消息在这里离开收件箱
const decision = await this.dispatch.waterfall("agent/pre-step", …);
if (decision.kind === "reject") return decision;               // ……并且再也不会被放回
```

循环在询问任何插件"这一步能否进入"**之前**就把该步骤的消息领取走了，而被拒的步骤不会把它们放回。一个只返回 `reject` 的刹车会静默地**从收件箱和会话日志里同时删除**操作者的提示词。

所以在拒绝之前，本插件把被领取的那批消息复制进一份持久台账，并在内存中保留逐字的消息对象。到放行时刻再把它们投递回去——第一条走 `agent.send(…, 'next-turn', true)` 以真正唤醒驱动器，其余走 `agent.inbox.append` 以保持顺序。

### 它不会和自动续跑插件打架

`dsh-client-auto-continue` 会在中断后自动重发「继续」，而且它跑在**宿主进程内**——把所有浏览器标签都关掉也拦不住它。对一个"拒绝看起来像中断"的刹车来说，这本来是真实的风险。但在这里不是，因为它自己文档写明的规则是：

> **绝不自动继续**：用户主动停止(`aborted`)或策略拒绝(`blocked`)

被拒的步骤以 `reason: { kind: 'blocked' }` 关闭其轮次，而那个插件刻意忽略这一种。所以刹车不需要与它做任何协调——但这个交互是一条**回归断言**，不是一个假设。

## 安装

需要 Node.js ≥ 20，以及一个 `dsh plugin` 命令可用的 DeepSeek Harness 构建。

```sh
dsh plugin --profile web add link:D:\SoftDocument\DSHProject\PeakStopValleyStart
```

之后重启 harness，让 profile 的层栈重新装配。

卸载：

```sh
dsh plugin --profile web remove dsh-peak-valley-brake
```

### 同一个 `$DSH_HOME` 只能跑一个 harness

这不是本插件的属性，但它决定你怎么测它，所以记录在此。

**同一个 `$DSH_HOME` 同时只能跑一个 harness。** 第二个实例会在插件树加载阶段失败：

```
failed to apply loader entry ui-task-board (@linxin666/dsh-client-ui-task-board):
  task-board ledger is already owned by process 13120
```

`@linxin666/dsh-client-ui-task-board` 对 `$DSH_HOME/task-board/ledger-v2.lock` 加了独占进程锁，记录 PID 与属主进程的启动时刻。第二个 harness 拿不到锁，**整个启动中止**。这把锁是刻意的保护，而不是绕过去的障碍：两个 harness 共写同一个 task-board 账本会把它损坏。删掉锁文件只是把损坏风险转移到你的任务板上。

这个坑在测本插件时特别容易踩中：插件装进的是**一个 profile**，而 profile 只在启动时重新装配——所以你必须重启 harness 才能加载它，而**重启恰恰被锁阻止**（另一个实例还活着）。当桌面应用在跑时尤其容易掉进去：**DSH Desktop 自己的 harness 跑的就是 `dsh … web`，而 `web` 正是你刚装插件的那个 profile。** 于是应用与终端争同一把锁。

两条出路：

1. **重启桌面应用，而不是开终端实例。** DSH Desktop 加载同一个 profile，所以插件会出现在它的界面里，不需要第二个实例。
2. **给第二个实例独立的 `DSH_HOME`。** 这样各持自己的锁：

   ```powershell
   $env:DSH_HOME = "$env:USERPROFILE\.dsh-web"
   dsh --profile web
   ```

   注意独立 home 有自己的 `settings.yaml`，所以本插件的 `locale: auto` 会在那边重新推导语言，而不是继承你应用里的选择。若在意，显式钉住 `locale: zh` 或 `locale: en`。

## 配置

在 profile 的 `cordis.patch.yml` 里加一条按 `id` 定位的条目即可修改下面任何一项。每个字段都有默认值，**不配置也能用**。

| 字段 | 默认值 | 含义 |
|---|---|---|
| `enabled` | `true` | 总开关。关闭时刹车永不拦截。 |
| `brakeLeadMinutes` | `5` | 在峰时窗口开启前多少分钟武装。 |
| `releaseDelayMinutes` | `1` | 峰时窗口关闭后再扣住多少分钟。 |
| `holdUserMessages` | `true` | 扣住你手动输入的提示词。可再生唤醒（goal round、提醒）一律放行。 |
| `verifyWorkspaceOnResume` | `true` | 重投递前检查工作区是否被外部改动。 |
| `allowManualOverride` | `true` | 允许 `/peak-valley` 命令提前放行被扣工作。 |
| `announceOnBrake` | `true` | 拦截时在对话中投递一条回执。 |
| `locale` | `auto` | 面向操作者文本的语言：`auto`、`zh` 或 `en`。 |
| `releaseTickSeconds` | `30` | 当调度表没有未来边界时的重新评估周期。 |
| `home` | `$DSH_HOME` 或 `~/.dsh` | 停机台账的写入位置。 |
| `peakWindowsOverride` | `''` | 应急出口：替换内置时段表。 |
| `debug` | `false` | 同时把守卫决策写入 stderr。 |

```yaml
- id: peak-valley-brake
  config:
    brakeLeadMinutes: 10
    releaseDelayMinutes: 2
```

#### 用 `id` 定位配置，绝不要用 `insert`

行式插件已经通过自己的 bundle patch 插入了它那一行。再加一条就会让**整个启动失败**：

```
failed to apply loader entry peak-valley-brake (dsh-peak-valley-brake):
  duplicate loader entry id: peak-valley-brake
```

所以上面那条是**按 `id` 定位、覆盖已存在的那一行**，而不是"新增一行"的指令。写成 `- insert: [{ id: …, name: … }]` 看起来等价，其实不等价——加载器会插入第二行同 id 的条目，然后拒绝整个 profile。

这个坑值得知道，因为报错点名的是**插件**而不是补丁条目，第一眼看上去像是插件本身的缺陷。

### 如果 DeepSeek 改了时段

时段表是内置的，为的是让守卫在无网络时行为完全可预测——这留下一个风险：官方改规则后，内置表在新版本发布前都是错的。`peakWindowsOverride` 补上这个缺口。它接收一个 UTC 分钟制窗口的 JSON 数组，运维当天就能响应：

```yaml
- id: peak-valley-brake
  config:
    peakWindowsOverride: '[{"weekdays":[1,2,3,4,5],"startMinute":60,"durationMinutes":180}]'
```

`weekdays` 为 0=周日…6=周六，`startMinute` 是 UTC 当日分钟数（60 = 01:00），`durationMinutes` 必须让窗口留在同一个 UTC 日内。**格式错误的覆盖会在加载时被拒绝，而不是被忽略**——刚得知规则变了的运维，不能被留在一个"以为覆盖生效了"的错觉里。

### 放行时的工作区漂移

一次停机可能持续数小时。如果人类在这个窗口里改了文件，agent 对工作区的认知——冻结在它的会话历史里——就变错了，它会针对一个不再匹配的世界复工。这正是这条检查要防的失效模式。

停机时刹车给工作区留指纹；放行时重新测量并告诉模型什么动了：

```
[peak-valley-brake] 这条请求被峰时拦截期间，工作区发生了变更。
请勿依赖你先前读取到的文件内容；在修改之前先重新读取受影响的文件。
- 已修改与未跟踪文件的集合发生了变化
发生变更的路径：
- src/parser.ts
```

指纹由两个事实构成，选它们的理由是便宜且不易被骗：

1. **`HEAD`** —— 抓切分支、抓停机期间产生的提交。
2. **`git status --porcelain --untracked-files=all`**，归约为一个摘要 —— 抓被改/新增/删除/新建的文件，**包括 agent 从没碰过的文件**。这才是关键信号，因为真实场景就是人类在峰时窗口里手改代码。

`.git/index` 的 mtime **刻意不**纳入：运行 `git status` 自身会刷新那个文件，于是对未改动仓库的两次测量会互相矛盾，守卫会在每次放行时误报漂移。有一条回归断言要求连续十次测量必须一致。

三条性质是承重的：

- **只提示，绝不阻断。** 漂移给工作加注解，绝不扣住工作。一个以"让工作继续"为职责的守卫，不能变成工作停摆的原因。
- **"无法校验"不等于"未变更"。** 非 git 仓库的工作区、或没有工作目录的会话，会如实报告"查不了"，而不是暗示什么都没变。**完全没有**工作区的会话不会收到任何提示——那里没有文件会过期，每次都警告纯属噪音。
- **只记路径，绝不记内容。** 台账记录仓库相对路径，绝不记录绝对路径，绝不记录文件文本。

只有相对路径进入台账，因此共享的台账不会泄漏目录结构。

### 漂移检测看不见什么

因为信号就是 `git status`，它继承了该命令的盲区。知道这些比知道它的顺利路径更重要：

- **被 `.gitignore` 忽略的文件是隐形的。** 创建或编辑它不会让 `git status` 发生任何变化，守卫会报 `unchanged`。这是一致的——被忽略的文件按定义就是 git 不跟踪的文件——但如果某个构建步骤把你在意的东西写进了被忽略的路径，这就是真实缺口。
- **停机期间创建又删除的文件是隐形的**，因为净状态相同。
- **仓库之外的改动是隐形的。** 检查范围是会话的工作目录；同一时间窗里被改动的兄弟项目不会被报告。
- **会话从未拥有过的仓库**会永远报 `unverified`，每次放行都带一条重读提示。这很诚实但也很吵——这正是"把插件自己的项目变成仓库"的理由，比如本仓库现在这样。

在真实仓库中，这条链路已端到端验证：创建一个未跟踪文件产生 `drifted` 并列出该路径；创建一个被忽略的 `.tmp` 文件产生 `unchanged`。

### 查看守卫在做什么

宿主的日志并非在所有启动方式下都可见，所以守卫可以把它自己的决策写到启动 harness 的那个终端：

```sh
DSH_PEAK_VALLEY_BRAKE_DEBUG=1 dsh web
# [peak-valley-brake] 已武装；当前 峰时（提前刹车 5 分钟，延后放行 1 分钟）
```

这行启动日志也是确认"插件真的加载了"的最快方式。

### 在对话里看到什么被扣下了

刹车扣住请求时，会往对话记录里投一条回执，所以"被扣住"永远不会长得像"卡死"：

```
[peak-valley-brake] 当前 API 处于峰时计价，已拦截 2 条消息。
它们只是排队、并未丢失，将于 2026-09-15 12:01（UTC+8，即 2026-09-15 04:01 UTC）自动放行。
如需立即放行，请执行 /peak-valley 命令并传入参数 "now"。
```

它以**面向模型的上下文**注入，而不是排队成一次唤醒——一次 followup 会唤醒驱动器，然后被这个刹车自己拒绝。它携带 `source.form: 'notice'`，因此宿主把它渲染成一条折叠的通知行，而不是操作者说的话；其摘要受宿主 120 字符上限约束。

**每个停机窗口只投一次**：每次唤醒都投会把安静的等待变成满屏重复通知。`announceOnBrake: false` 可关闭。

### 语言

每一条人读的消息——回执、漂移提示、`/peak-valley` 输出——都来自一份双语字典。`locale: auto` 按以下顺序解析：

1. 宿主持久化在 `$DSH_HOME/settings.yaml` 里的 UI 语言（若有）。这才是真正的答案，因为它是操作者在 GUI 里实际选择的。
2. `LC_ALL`/`LC_MESSAGES`/`LANG`/`LANGUAGE`，然后是运行时的 ICU 区域，再然后是 Windows 注册表里的用户默认 UI 语言。这些都只是对 UI 语言的**猜测**，所以排在设置项之后。
3. 英文。

设 `locale: zh` 或 `locale: en` 可无视机器报告、钉死语言。日志行**刻意不翻译**、保持英文：它们是终端里读的诊断信息，语言稳定才便于 grep。

`test/locale.test.mjs` 断言两份字典在**每一层键位完全一致**，且没有中文条目残留未译的 ASCII——漏译否则会在句子说到一半时静默失效。

### 现在放行：`/peak-valley`

有时工作等不到谷时。`/peak-valley` 命令就是应急出口：

| 调用 | 效果 |
|---|---|
| `/peak-valley` 或 `/peak-valley status` | 当前档位、是否拦截及原因、下次调度切换、本会话滞留条数、以及当前覆盖状态 |
| `/peak-valley now` | **只放行一次**被扣工作。你发的下一条消息仍会被拦截 |
| `/peak-valley window` | 放行到下一个调度边界为止，便于连续对话 |
| `/peak-valley cancel` | 撤销覆盖，调度重新接管 |

**`now` 与 `window` 不是同一个命令，差别很容易踩。** `now` 只放行队列一次，适合"把这一件事先送进去"。如果你正在对话中途，要的是 `window`——因为 `now` 会扣住你的下一条消息，而那看起来就像命令失效了。回执里同时列出两者，正是因为这个。

**为什么是斜杠命令而不是模型工具**：刹车在模型运行**之前**就拒绝了步骤，所以"模型能调用的工具"恰恰在需要它的时候不可达。Harness 命令直接对 agent 执行、不产生模型消息、零 token 成本——这使它成为刹车生效期间唯一还够得着的入口。

三条性质让覆盖保持诚实：

- **它会自行到期。** 两种覆盖都只活到下一个调度边界——守卫不可能被永久关掉，也不需要任何人记得重新打开。
- **它可审计。** 每一次"调度本应扣住却放行"都会追加进插件数据目录下的 `overrides.ndjson`：哪个会话请求、何时授予、何时用尽、当时档位如何分类。跳过成本策略是操作者的决定，但不该是个隐形的决定。记录写在**追加式文件**而不是会话台账里，因为台账会被它所描述的那次投递本身删除。
- **它可以被拒绝。** `allowManualOverride: false` 让命令返回错误而非照办，运维可用它保证任何命令都无法绕过自己的成本策略。

覆盖**绝不跨重启存活**：它是进程本地状态，因为刹车存在的全部意义就是它会自己重新武装。

## 状态徽章

插件还会在 Web UI 角落放一个徽章：角色形象即守卫状态，悬停后浮出的工具栏提供与斜杠命令完全相同的操作。

| 形象 | 含义 |
|---|---|
| `idle` | 谷时，没有扣下任何东西 |
| `armed` | 处于峰前提前量内，刹车即将落下 |
| `held` | 峰时，正在扣住工作 |
| `released` | 刚放行了被扣住的工作 |

悬停角色即出现工具栏：状态、放行一次、放行到谷时、撤销覆盖。每个按钮都跑与该子命令**同一个**处理函数，因此按钮与命令行不可能对同一操作给出两种说法——返回内容会以命令自己的措辞显示在气泡里。拖动角色可移动位置，单击可开关气泡，两者都按浏览器记住。

覆盖生效时即使没有扣住任何东西也会显示。它是唯一一种**故意在峰时花钱**的状态，徽章不允许自己对它保持沉默。

角色会轻微呼吸、脚下有接地阴影，并带一颗**玻璃状态珠**——光晕、半透明外壳、高亮核心、一点白高光——其中**光晕半径就是状态的强度**。安静的状态不占注意力，而唯一真正烧钱的那个才最响。状态珠用的是系统状态色而不是主题 token，这是刻意的：会随主题漂移的状态色就不再是信号。其余表面一律取自主题。

角色上方那块面板是**小仪表盘**而不是一句话：带标题与 LIVE 胶囊的头部、一条细分隔线，然后六行——当前档位、调度决策、下次切换、放行时刻、滞留消息、手动覆盖。每一行都由已发布状态回答，这也是宿主必须发布「下次切换」的原因：浏览器没有时段表，也没有能和宿主对齐的时钟。

**状态珠与面板上的标记回答的是两个不同的问题，而设计稿同时画了两者。** 状态珠说的是**徽章在做什么**——什么都没做时是灰的、拦截中是蓝的、只有覆盖在故意烧钱时才是红的——光晕半径承载强度。面板上的档位标记说的是**档位是什么**，其中谷时是绿色，因为便宜就是好状态。若两者共用一个颜色，"便宜"和"什么都没发生"就会长得一模一样。

下方是四格药丸按钮条，每格一个图标压在文字上。被选中的那格比它所在的条**更亮**而不是更蓝（设计稿就是这么画的），而它标的是"状态"——这恰好也是唯一一个永远不会不可用的操作。标记通过 `aria-pressed` 传递，这既是样式表挂钩的属性，也是读屏软件需要的语义。不可用的操作**变暗而不是消失**，因为这条本身同时就是当前状态的说明。

**结构用内联样式，样式表只负责装饰。** 本项目无法观察注入的样式表在操作者浏览器里是否真的生效，因此凡是徽章**形状**依赖的东西一律写成内联样式——那才是其余几何信息已经信任的机制。一行之所以是一行，如果只因为某个 class 说了 `display: flex`，那么样式表一旦不生效，它就会变成三块堆叠的方块——这正是面板标签/数值对齐失效的原因。注入的 `<style>` 里只留下内联样式真正表达不了的东西：关键帧、`:hover`/`:focus-visible`/`[aria-pressed]`、带前缀孪生属性的 `backdrop-filter`，以及一段 `prefers-reduced-motion`。有一个用例专门挂载到**拒绝 `<style>` 的 document** 上，断言面板仍然是面板。

样式表还会给自己打上 `data-plugin` 标记：加载器会把所有**未被认领**的 `<style>` 打上「下一个物化的客户端插件」的 id，并在那个插件卸载时删掉它的样式——没有标记的样式表，离被某个毫不相干的插件重载顺手删掉只差一次操作。

玻璃表面用 `color-mix` 从主题 token 混出来，因此同一条规则在浅色页和深色页上都能结霜；`color-mix` 不被支持时该声明会被丢弃，面板变得朴素但仍可用。本徽章早先的版本用了自己编的 token 名——`--dsw-surface` 之类，全都**不存在**——结果在暗色主题下变成一块白板且毫无征兆；现在任何不是真实 token 的 `var(--…)` 都会让断言失败。

### 为什么是浏览器问宿主

在浏览器里直接读 `peakValleyBrake` 投影是最直观的设计，但它行不通。这个 harness 的客户端半边只提供 `connection`、`locale`、`theme`、`chatFileMentions`、`sessionLogDownload`，以及 cordis runner 自己的两个服务——**没有**会话注册表，也**没有**投影注册表。客户端插件若声明了一个没人提供的服务，就会被一直挂着等它出现，于是永远不激活：徽章就是**根本不出现**，而且任何地方都不会报错。

所以状态改走 `POST /api/peak-valley-brake.action`。宿主答得出来，因为那两个服务都在宿主侧，也因为只有宿主知道操作者正在看哪个会话。徽章的第一次轮询不带会话 id，宿主回一个，此后徽章就一直带着它。每个响应都附带当前状态，因此「执行动作」与「刷新显示」是一次往返而不是两次。

### 徽章为什么待在同一道围栏之内

路由注册在 `/api` 下，这个前缀在本 harness 里只有一个所有者：由它先做浏览器认证与 `Host`/`Origin` 校验，再分发给注册过的精确路径。注册在别处就会站到围栏之外；而 `/api` 下未被认领的路径返回 404，不会落到别的所有者手里。动作词表是封闭的——`poll`、`status`、`now`、`window`、`cancel`——因此畸形或恶意请求无法把任意输入送进命令处理函数。

### 设置页面

设置 → 峰谷刹车 里有三项偏好：是否显示角色、角色多高、鼠标移开后工具栏停留多久。它们存放在 harness 自己的设置面里——`$DSH_HOME/settings.yaml`，命名空间 `peak-valley-brake`——正因如此每个字段才有「恢复默认」，选择也能跟着你到另一台机器。

该页面占用 `settings.section` 槽位，因此它排在设置导航里与内置分区并列，并且只在被选中时挂载。这个槽位是由设置外壳**挂载时**声明的，而不是由某个包声明，所以必须经 `slots.inject` 取得；直接 `register` 会找不到这个槽。槽位占用者必须是 React 组件，因此页面用的是宿主自己的 React——构建时把 React 标为 external，否则打进第二份会让页面出现两个 React 实例，所有 hook 都会抛错。

有两处是**刻意可选**而不是必需。`slots` 与 `settingsScope` 声明为 nullish，而 cordis 会完全跳过 nullish 的注入项（`if (isNullable(config)) continue`），所以没有设置面的部署仍然会挂载徽章，而不是把插件永久挂起。另外 schema 里**不写** `min`/`max`：schemastery 对越界值是**拒绝**而非钳制，而设置服务在注册时就会解析整个命名空间——否则一个手改过的 `settings.yaml` 就能为了一个外观偏好把刹车整个拖垮。范围改为在真正使用这些值的地方强制执行。

## 为这个 harness 写插件

三条契约花了真实的调试时间才摸清，且都以**不指向病因**的报错失败。记录在此，因为本生态里任何插件都会撞上。每一条都由 `test/manifest.test.mjs` 断言，因此后续修改无法悄悄把它们带回来。

**1. `Config` 必须实现 Standard Schema，不能是普通对象。** cordis 通过调用 `Config['~standard'].validate(raw)` 解析配置。普通对象描述符会产生：

```
failed to apply loader entry <id>: Cannot read properties of undefined (reading 'validate')
```

zod 的 object schema 直接满足这一要求，所以这里的 `Config` 就是它。

**2. 没有 `config:` 键的行会校验 `undefined`。** 只用 object schema 会以 `expected object, received undefined` 拒绝，使得插件在不配置的情况下无法安装。`.default({})` 看起来是解法但不是：它在校验**之后**替换，返回一个没有套用字段默认值的空 `{}`。`prefault({})` 在校验**之前**替换，因此字段默认值仍然生效。所以导出的形状是 `ConfigShape.prefault({})`。

**3. 你读取的每一个服务都必须声明在 `inject` 里，即使它是可选的。** 读取未声明的服务会抛：

```
failed to apply loader entry <id>: cannot get property "commands" without inject
```

`if (ctx.commands === undefined)` 帮不上忙——异常发生在属性读取那一刻。但把依赖声明为**必需**又会让它无法在任何缺少该服务的组合中加载，对一个必须也能 headless 运行的插件来说更糟。cordis 把**空值的 inject 视为可选**（`if (isNullable(config)) continue`），所以正确的写法是：

```js
export const inject = { commands: null };
```

……然后防御性地读取它，因为可选服务在非活动上下文中仍可能不可用：

```js
const probeCommands = () => {
  try { return ctx.commands } catch { return undefined }
}
```

### 为什么要有提前量与延后量

请求按**被处理**时刻的费率计费，而不是按发出时刻。一条 `11:59` 发出、`12:00` 返回的请求按峰价计费。5 分钟提前量防止刹车被这个竞态击穿，1 分钟延后量防止它在放行时踩进同一个坑。如果你的请求经常超过五分钟，把提前量调大。

## 它不做的事

- **峰时并非零成本。** 刹车装在根 agent 上，不管辖子代理、后台作业或已在飞的 workflow。峰时开始那一刻已经发出的工作会跑完，并按峰价计费。保证是**峰时不新开请求**，而不是"峰时不花钱"。
- **它不关闭 harness。** 没有进程管理、没有计划任务。自动复工的前提是宿主仍在运行。
- **跨宿主重启被扣下的提示词会以摘要形式回来，而非逐字。** 台账能跨重启，但确切的消息对象不能。投递的是一份**明确标注为重建**的内容。在同一个进程生命周期内，原文精确保留。
- **时段表是内置的。** 它于 2026-09-15 与官方页面核对过。若 DeepSeek 修改窗口，本插件需要发版——它刻意不抓取页面，以保证行为可完全离线预测。
- **被扣的提示词在等待期间不会出现在聊天流里**，直到被投递。它已被记录并会重新投递，但对话在此之前不显示任何东西。可以看插件日志行，或运行 `/peak-valley status`。

## 故障即放行保证

成本守卫绝不能成为工作停止的原因。每一条降级路径都是**放行**而不是拒绝：

| 故障 | 行为 |
|---|---|
| 台账写不进去 | 步骤进入；原因被记录。拒绝会销毁一份无法保存的提示词。 |
| 放行时台账读不出来 | 这一趟不投递任何东西；批次留在磁盘上等下一次。 |
| 重投递抛错 | 台账**不**清除，批次在下一次放行趟次重试。 |
| 安装监听器时抛错 | 该 agent 不被守卫，失败被记录。 |

它们也不需要 harness 在运行，因此完全绕开了"同一 `$DSH_HOME` 只能跑一个 harness"这条约束——`npm test` 是不碰活动 profile 就能检查本插件的最快方式。

## 限制与已知风险

- 峰时边界上已在飞的子代理按峰价计费（见上）。
- 刹车管辖的是插件加载**之后**创建的根 agent；热重载之前就存在的 agent 不会被接管。
- 只存在于收件箱里的工作——驱动器会重新发出的 goal round——被刻意放行而非扣住，因为扣住它会和重新生成它的驱动器抢跑。
- 放行定时器是一个共享定时器，在每个边界**从当前时钟重新武装**而不是累加，因此系统时钟变更只会改变答案，不会把状态弄坏。
- 漂移检测需要 git。在不是仓库的工作区里它报告"无法校验"而不是猜测，于是模型被告知重读，而不是被告知发生了变更。
- 回执以面向模型的上下文注入（`source.form: 'notice'`），因此它在对话记录里表现为一条折叠通知，而不是一条聊天消息。它的渲染已对宿主消息类型核实、并与宿主内某插件已在用的形状比对过，但尚未在真实对话中被观察到。
- 徽章的**外观**没有被本项目观察过。它进入真实启动图、它满足的 loader 契约、以及它在假 document 上的行为都有断言；它在浏览器里长什么样由人来确认。
- 徽章是**轮询**的。推送通道需要客户端半边并不提供的订阅能力，所以页面开着的代价是每隔几秒一次很小的、带认证的请求。

## 开发

测试套件不需要 harness、不需要网络、不消耗任何 API 额度——它是不碰活动 profile 就检查改动的最快方式。`npm test` 跑全部十三个文件；每个文件也能单独运行，迭代时用后者更顺手。

### push 前闸门

每次 push 前会自动跑 `npm test`，失败就**拒绝推送**：

```
pre-push: running the test suite (SKIP_TESTS=1 to bypass)...
pre-push: suite passed
```

它跑**全部**套件，而不是去猜这次改动影响哪些测试。七个互相独立的文件跑完不到一分钟，而一个"自己判断哪些测试重要"的闸门就是有洞的闸门。跑全部的成本每次 push 只付一次；漏掉那一个关键测试的成本由拉取的人承担。

提交进仓库的钩子需要每个 clone 做一次设置，因为 `core.hooksPath` 是本地 git 配置，clone 不会带过来：

```sh
npm run hooks:setup
```

它把 `core.hooksPath` 指向已提交的 `.githooks/` 目录，并给钩子加上可执行位。不做这一步该目录就是**惰性的**——git 仍然只看 `.git/hooks`，那里没有任何提交内容，因此也传不到别人手上。

真遇到紧急情况需要绕过：

```sh
SKIP_TESTS=1 git push
```

它是刻意写成显式变量的，而不是挂到 `git push --no-verify` 上——后者会连带绕过你以后可能想保留的其他钩子。

`.githooks/**` 在 `.gitattributes` 里被钉为 LF。CRLF 的 shebang 会让 Git Bash 去找一个名为 `/bin/sh\r` 的解释器，钩子以 `bad interpreter` 失败——那种报错看起来像仓库坏了，而不像行尾问题。

### 徽章形象素材

徽章的角色素材放在 `assets/mascot/`。那里的根目录文件是全尺寸原图；带数字的子目录（`128/`、`200/`、`320/`）是按徽章实际渲染高度生成的派生图，每个状态一张：

| 文件 | 对应的状态 |
|---|---|
| `idle.png` | 谷时，没有拦截 |
| `armed.png` | 峰前刹车窗口内 |
| `held.png` | 峰时，正在拦截 |
| `released.png` | 刚刚放行 |

改动任一张原图后重新生成派生图：

```sh
pwsh -File scripts/resize-mascot.ps1
```

它刻意使用 `System.Drawing` 而不是 `sharp`：`sharp` 虽然装在桌面应用的 `node_modules` 里，但它是针对 Electron 的 Node ABI 编译的，普通系统 Node 加载不了。脚本写出 32 位 ARGB，所以抠图背景保持透明——背景若被压平，徽章后面就会出现一个色块。

`test/assets.test.mjs` 断言每个状态在每个尺寸下都有素材、每个文件都是真正的 PNG 且不超过体积上限、并且素材目录与状态清单一致。这些断言之所以存在，是因为**在浏览器里，缺文件不会表现为测试失败，而是一个静默空白的徽章**——而这恰恰是本项目自己无法观察到的部分。
