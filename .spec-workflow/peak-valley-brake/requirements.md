# 需求研究结论：峰谷自动刹车（peak-valley-brake）

- 日期：2026-09-15
- 状态：关键决策已全部收敛，可进入 `to-spec`
- 目标形态：DeepSeek Harness 插件（`dsh plugin` 可安装，host + client 双端）

## Git 入口记录

- Git 仓库路径：无
- Git 入口：not a git repo
- 分支决策：不适用（无仓库，无分支操作）
- 脏工作区处置：不适用
- 结论：本阶段不产生任何提交，后续阶段也不会因分支产生额外约束

## 背景

DeepSeek 官方对 API 实行峰谷分时定价（[官方定价页](https://api-docs.deepseek.com/quick_start/pricing) 脚注 (3)）：

| 项 | 官方口径 |
|---|---|
| 峰时 | UTC `01:00–04:00`、`06:00–10:00`，**周一至周五** |
| 谷时 | 其余全部时间（含周六、周日全天） |
| 价差 | 谷价 = 峰价的一半 |
| 受影响模型 | `deepseek-flash`、`deepseek-v4-pro`（两者峰谷规则一致） |

换算成北京时间：峰时为工作日 `09:00–12:00`、`14:00–18:00`；工作日谷窗为 `00:00–09:00`（扣掉 09:00 前的衔接）、`12:00–14:00`、`18:00–24:00`。

现状问题：编码任务（尤其是 goal 驱动的无人值守多轮推进）会在峰时段持续产生模型请求，全额按峰价计费。用户希望峰时自动停工、谷时自动复工，且跨峰谷的衔接不能损坏工程状态与会话状态。

### 已核实的关键外部事实（推翻了网上大量旧资料）

1. **旧规则不可用**：网上广泛流传"错峰时段为 UTC 16:30–00:30"（2025 年旧方案）。当前官方口径已变为上表的工作日双峰窗。**任何按 UTC 16:30–00:30 实现的方案都是错的。**
2. **判定必须按 UTC**：官方以 UTC 定义窗口；北京时间为 UTC+8。
3. **周末全天谷时**：周六、周日（UTC 自然日）无峰谷切换。

### 已核实的 DSH 宿主能力（决定了可行边界）

| 能力 | 结论 | 来源 |
|---|---|---|
| 步骤准入钩子 | `agent/pre-step` 可返回 `{ kind: 'reject' }` 拒绝即将进入的步骤 | `@deepseek-ai/dsh-agent` README「步骤准入」 |
| **拒绝会吃掉消息（实测修正）** | 循环在 `preStep` 里**先 `inbox.claim()` 再跑 `pre-step` 瀑布**，拒绝时被领取的消息**既不回 inbox、也不写会话日志**。故"拒绝无损"不成立，必须由插件自己保存后重投递 | `dsh-agent-loop/lib/index.js` 第 889/894/903 行；类型注释「若该步骤被拒绝，被领取的消息到此结束」 |
| 补回 inbox 会热循环（实测） | `turn()` 末尾 `if (!this.inbox.hasPending) return false;`，而 `kick()` 是 `while (await this.turn())`。故峰时把消息补回 inbox 会导致每轮写 `turn/start`+`turn/end` 的快速循环——**峰时只能存不放** | 同上 第 872 / 1002 行 |
| 拒绝的收尾标记 | 拒绝使 `turnEnds = { kind: 'blocked' }`，正是 `dsh-client-auto-continue` 声明"绝不自动继续"的两种之一 | 同上 第 941-943 行 |
| 唤醒入口 | `Agent.send(message, target, wakeup)` 是公开的、可唤醒的投递路径；`inbox.append` 不唤醒 | `dsh-agent` 类型 `Agent` 接口 |
| 消息来源可区分 | `kind:'user'` 为用户消息，`kind:'plugin'` 携带 `plugin` 名 | `@deepseek-ai/dsh-llm` `MessageSourceMap` |
| 步骤粒度 | 工具执行在步骤的模型请求**之后**；在下一步边界拒绝 = 当前步骤（含工具）已完整跑完 | `dsh-agent-loop` `step()` |
| 硬中断限制 | 只有整轮 `cancel(cause)`；**不存在"只中止当前步骤、保留整轮"的接口** | `dsh-agent` README「已知限制」 |
| 崩溃恢复 | 会话检查点策略保证：模型请求前、工具产生外部副作用前均已持久化；崩溃后**中断的工具调用以"未知结果"恢复，绝不自动重试** | `@deepseek-ai/dsh-session-checkpoint-policy` README |
| 自动续行 | `dsh-goal-round-driver` 在 agent 空闲且 goal 为 active、续行已启用、额度未耗尽时自动排入 goal round | `@deepseek-ai/dsh-goal-round-driver` README |
| 会话内持久提醒 | `dsh-schedule` 提醒重启后仍在，但**冷会话不触发**，交付需 live 根 agent | `@deepseek-ai/dsh-schedule` README |
| 已装插件的干扰 | 本机已装 `dsh-client-auto-continue@0.11.6`，会在"非人为中断"后自动发送「继续」 | 本机 `profiles/web/package.json` |

### 成本节省的诚实边界

- 刹车只装在**根 agent** 上，插件不接管已由根 agent 发起的子代理/后台作业/workflow。
- 因此"峰时零成本"**不成立**：峰时已在飞的子代理调用仍按峰价计费，只能保证"峰时不新开"。
- DSH 进程未运行时，没有任何机制能替用户启动它；"谷时自动开工"的上限是"DSH 保持运行"。

## 目标

1. **峰时不新开工作**：以 UTC 官方时段为准，提前 5 分钟停止发出新的模型请求，在整个峰时段内**零新增峰价请求**。
2. **停工不伤工程**：只在步骤边界停（工具已完整跑完），不使用任何会把工具腰斩的中断手段。
3. **谷时无错承接**：谷时到达后自动复工，且满足验收清单（连续性 + 不重复副作用 + 工作区漂移校验），不需要人工重新交代上下文。
4. **行为可预测**：时段判定、提前量、放行条件全部确定性可复算，不依赖网络。

## 非目标（本轮不做）

- 不做峰时"降级模型"式省钱（不切换模型/推理强度）。
- 不做 DSH 进程级休眠/唤醒（不关进程、不申请计划任务、不做开机自启）。
- 不做基于官方页面的在线抓取（时段表内置）。
- 不接管子代理/后台作业/workflow 的峰时成本（它们继续跑完）。
- 不做跨会话的全局面板，不统计历史峰谷省钱账单（仅记录状态与事件留痕）。
- 不做多用户/多租户与权限体系。

## 用户流程

### 主流程：无人值守的峰谷循环

1. **谷时**：用户给 agent 派活（普通消息，或创建 goal 让 `dsh-goal-round-driver` 自动多轮推进）。插件处于放行态，不干预任何步骤。
2. **峰前 5 分钟**：插件进入待停态：停止放行新的步骤准入，记录本次刹车的**工作区指纹**（见「数据语义」），并在对话中写入一条可见的停工说明（含峰时结束时刻）。
3. **峰时**：任何想进入的步骤（用户新消息、goal round、自动续行）一律被拒绝；消息原地留在持久 inbox，不被消费、不被丢弃。
4. **谷时到达后 1 分钟**：插件放行。被压住的工作在下一个边界自动准入并继续，**不需要用户重新发消息**。
5. **放行时校验**：重新计算工作区指纹并与刹车时对比；无漂移则直接继续；有漂移则注入一次"工作区已变更，先重读这些文件再动手"的上下文提示，再继续。

### 分支流程 A：峰时用户主动发消息

- 消息被拒绝 → **原地排队**，不发送、不计费。
- 对话内给出明确回执：现在是峰时、消息已排队、将于 `HH:MM`（北京时间与 UTC 双显）自动放行。
- 用户可**手动覆盖**：在对话内触发一次放行（对当前这一条/这一轮），插件记录覆盖事件后不再拦截该轮。

### 分支流程 B：谷时自动复工（无 active goal）

- 若会话内没有 active goal，`dsh-goal-round-driver` 不会自动续行。
- 此时依靠"被拒绝的消息仍在 inbox 中"这一事实完成承接：放行后循环在下一个边界重新准入同一批消息。
- 不额外发明第二套"继续"提示词机制（避免与 `dsh-client-auto-continue` 的「继续」重复注入、互相踩踏）。

### 分支流程 C：DSH 重启

- 插件状态从插件自有存储恢复，不依赖内存。
- 若重启后仍处峰时且仍有被压住的工作，继续拦截；若已进入谷时，放行。
- 若重启发生在峰时且工作区已被外部改动，放行时按流程 5 的漂移分支处理。

## 功能范围

### 1. 时段判定（纯函数，无副作用）

输入：UTC 时刻、内置峰窗表、配置的提前量/延后量。
输出：当前档位（peak / off-peak）、下一次切换时刻、距切换的剩余时长、当前是否处于"待停"窗口。

判定规则（必须精确实现）：

- 峰窗为工作日（UTC 周一至周五）`[01:00, 04:00)` 与 `[06:00, 10:00)`。
- `brakeLeadMs`（默认 5 分钟）：在峰窗开始前 5 分钟即视为"待停"，不再放行新步骤。
- `releaseDelayMs`（默认 1 分钟）：峰窗结束后再延迟 1 分钟才放行，用于覆盖"请求跨边界、计费时刻落在峰窗内"的漏计费风险。
- 周六、周日（UTC 自然日）全天谷时，无待停窗口。
- **边界正确性要求**：`[start, end)` 半开区间；`04:00` 整点属谷，`01:00` 整点属峰；跨周一边界必须由"上一个峰窗结束 + 周末"正确推导，不得因周末判断把周一 `01:00` 前的 5 分钟待停窗口吞掉。
- 时区要求：判定只用 UTC；展示用的北京时间由 UTC+8 固定偏移换算，**不使用本机时区**（避免 DST 与用户改系统时区导致的行为漂移）。

### 2. 步骤刹车（host 端）

- 注册 `agent/pre-step` 监听器；处于待停/峰时态时返回 `{ kind: 'reject' }`。
- 除拒绝外**不产生任何副作用**：不动 inbox、不 cancel、不写会话事件、不杀工具。
- 放行态下必须**完全透明**：不改变消息批次、不改变 `startsRequestSeries`、不增加任何请求材料（保证 KV cache 前缀稳定）。
- 插件的 `pre-step` 监听器必须把下游的 `enter` 决策原样透传，不做任何包装改写。

### 3. 复工与漂移校验（host 端）

- 刹车时记录工作区指纹（见「数据语义」），持久化。
- 放行时重算指纹并比对：
  - 一致 → 直接放行，不注入任何内容。
  - 不一致 → 通过 `inject()` 注入**一次**提示（不唤醒驱动器），内容为"工作区在你停工期间发生了变更，继续前先重读以下文件/路径"。注入内容需列出发生漂移的具体路径，而非泛泛提醒。
- 漂移校验只影响提示，**不得阻断复工**（用户的核心诉求是能接着干，不是被卡住）。

### 4. 对话内回执与手动覆盖（host + client）

- 拦截可见化：不得静默吞消息。对话中写入停工回执，包含：当前档位、峰时结束时刻（北京时间 + UTC）、被压住的工作条数、手动覆盖入口提示。
- 手动覆盖：用户可在对话内执行一次放行；覆盖只对当前这一轮生效，且必须留痕（谁在什么时刻覆盖、当时是峰时第几分钟）。
- 状态指示：client 端徽章显示当前档位、距切换倒计时、刹车是否生效；点开可见时段表与配置入口。

### 5. 配置项（插件设置卡）

| 配置 | 默认 | 含义 |
|---|---|---|
| `enabled` | 开 | 全局总开关 |
| `brakeLeadMinutes` | 5 | 峰前提前刹车分钟数 |
| `releaseDelayMinutes` | 1 | 峰后延迟放行分钟数 |
| `allowManualOverride` | 开 | 是否允许对话内手动覆盖 |
| `verifyWorkspaceOnResume` | 开 | 是否做放行时工作区漂移校验 |
| `peakWindowsOverride` | 空 | 官方规则变更时的应急覆盖（UTC 窗口表） |
| `announceOnBrake` | 开 | 是否写入停工回执 |

## 业务规则

1. **只拦新请求，不拦在飞任务**：峰时不再新开子代理/后台作业/workflow，但已发起的允许自然跑完（它们停不下来，强杀反而制造坏状态）。
2. **拒绝必须自保**：`pre-step` 拒绝会永久吃掉被领取的消息（见上表实测结论），所以插件必须在拒绝前把该批消息写入持久台账并在放行时重投递。这是"消息不丢"的唯一实现路径，不是可选优化。
3. **峰时只存不放**：被扣下的消息在峰时**不得**补回 inbox——`while (await this.turn())` 会因此形成快速循环并污染会话日志。补回动作只在放行时刻执行一次。
4. **只扣用户消息**：`kind:'user'` 的消息由插件保存并重投递；goal round、schedule 提醒、插件上下文等可再生的唤醒一律放行，交给其属主重新发起，避免与驱动器抢跑。
5. **不做二次"继续"注入**：复工复用既有唤醒机制（被扣消息唤醒 + `dsh-goal-round-driver`），插件不自己发明第三套续跑文案。
6. **不用 `cancel()`**：任何情况下刹车都不调用整轮取消，因为那会腰斩工具，违反"不能出错"。
7. **状态判定必须可复算**：给定 UTC 时刻与配置，任何人能独立算出相同档位；不依赖网络、不依赖本机时区、不依赖启动时刻。
8. **放行优先于完美**：台账写失败、读失败、重投递抛错、监听器安装失败——一律**放行并告警**，不得因为插件自身故障把用户永久卡在停工态。特别是台账写不进去时必须放行，否则等于用"省钱的插件"销毁用户的提示词。

## 数据语义

### 时段与时刻

- 权威时基：UTC。所有持久化的时刻一律为 UTC RFC 3339。
- 展示时区：固定 UTC+8（北京时间），双显时并列展示 UTC。
- 峰窗表内置为常量，随插件版本发布；改动需补版本号并在文档中记录变更依据与日期。

### 工作区指纹（漂移校验的判定依据）

- 计算时机：进入待停态时算一次并持久化；放行时重算。
- 内容（按稳定性从高到低，实现阶段可裁剪但必须覆盖前两项）：
  1. `git status --porcelain` 的完整输出（若工作区不是 git 仓库则跳过该项）
  2. 本轮 agent 触碰过的文件路径 + 其内容哈希（触碰来源：`edit`/`write` 类工具调用记录）
  3. 当前 `HEAD` 提交哈希（若为 git 仓库）
- 漂移定义：任一项与刹车时不一致。
- 漂移的语义：工作区在停工期间被外部（人、IDE、其他工具）改动，会话内对文件的认知可能过期。
- 指纹不可得时（非 git 仓库、工具记录缺失）：记为"未知"，放行时不做漂移阻断，只标注"未校验"。

### 状态与留痕

- 需要跨重启存活的：当前刹车是否生效、本次刹车的开始时刻、刹车时指纹、被压住的工作条数、手动覆盖记录。
- 需要留痕可审计的事件：进入待停、进入峰时、放行、手动覆盖、漂移检出、插件自身降级（放行+告警）。
- 成本口径说明：本插件**不重算费用**；若需要"省了多少钱"的数字，只能基于 token 用量与官方价目表的估算，且必须在展示上标明是估算值。

## 权限、安全与审计要求

- 插件在用户本机、用户自己的 profile 内运行，不引入新的网络出站（时段表内置、不抓官方页）。
- 不读取、不传输、不落盘 API Key 或任何凭据。
- 工作区指纹会包含文件路径与内容哈希：仅存本地插件存储，**不得包含文件内容明文**，不得随任何遥测/上报外发。
- 手动覆盖必须留痕：跳过成本策略属于用户对自己钱包的显式决定，需要可回溯。
- 插件不得读写用户工程之外的文件（指纹只覆盖当前工作区）。

## 异常与边界场景

| 场景 | 期望行为 |
|---|---|
| 峰前最后一步的请求跨过峰窗边界 | 由 `brakeLeadMinutes` 提前量覆盖；提前量不足时表现为漏计费，需在文档中提示可调大 |
| 用户在峰时连续发多条消息 | 全部原地排队，逐条给出排队回执；不重复刷屏（回执合并展示） |
| 峰时用户手动覆盖后又发新消息 | 覆盖只作用于被覆盖的那一轮；新消息仍按峰时规则排队 |
| `dsh-client-auto-continue` 在刹车后自动发「继续」 | **不得被触发**：刹车产生的收尾是策略拒绝（`blocked`），该插件明确不自动继续 `blocked` 与 `aborted`。此点必须专测 |
| agent 处于 goal 驱动的自动推进中，峰时到达 | `pre-step` 拒绝使该轮 goal round 不被准入；因未进入步骤，不消耗 goal 额度；谷时框架自动重新排入 |
| 峰时正当会话空闲、无任何排队工作 | 不产生任何事件、不写回执、不占资源，仅由计时器在边界唤醒 |
| 周六/周日全天 | 不刹车；但周日末尾必须正确预备周一 01:00（UTC）前的待停窗口 |
| 机器休眠/关机跨过整个谷窗 | 无解且不需要解：醒来后按当前真实档位重新判定；不得补跑错过的窗口 |
| DSH 在峰时被重启 | 状态从存储恢复并继续拦截；重启后若已谷时则放行 |
| 系统时区或时钟被改 | 判定不受影响（只用 UTC）；时钟跳变导致的判定抖动需以"重新判定"而非"累加计时"实现 |
| 插件自身异常（存储不可用、指纹计算抛错） | 降级为放行 + 告警，绝不把用户卡在停工态 |
| 非 git 工作区 | 跳过 git 相关指纹项，退化为"被触碰文件的哈希"，仍可检出人工改动 |

## 验收清单（"不能出错"的操作化定义）

1. **峰时零新增请求**：峰时段的模型请求数为 0（在飞任务除外，且需单独标注）。
2. **刹车无腰斩**：不存在被中断的工具调用；会话日志中无工具"未知结果"记录。
3. **不重复副作用**：复工后不出现同一工具被重复执行产生的重复副作用。
4. **消息不丢**：峰时被拒的消息在复工后原样进入模型历史，内容与顺序不变。
5. **自动复工**：谷时到达后无需用户重新发消息即可继续（goal 场景与普通场景各验一次）。
6. **漂移可检出**：刹车期间在工作区改动文件，复工时能正确检出并给出具体路径。
7. **不误触发 auto-continue**：刹车收尾不引发 `dsh-client-auto-continue` 自动发送「继续」。
8. **判定可复算**：给定 UTC 时刻，档位与切换时刻与官方口径逐条对齐（含周末、周一边界、整点边界）。
9. **重启不丢态**：峰时重启 DSH 后仍能继续拦截，谷时重启后能正常放行。
10. **故障即放行**：人为制造存储/指纹异常，验证插件降级为放行而非卡死。

```

```

即：模块被加载、Config 通过 Standard Schema 校验、`inject` 声明被接受、`apply()` 执行、`/peak-valley` 命令注册成功、调度逻辑在真实时钟下运行。

这次验证抓出了**三个静态检查与自建假宿主都无法发现的真实缺陷**，均已修复并加断言：

1. `Config` 不能是普通对象描述符——cordis 走 Standard Schema（`Config['~standard'].validate`），否则 profile 启动直接失败。
2. 无 `config:` 键的行会让宿主校验 `undefined`；且 `.default({})` 是错的（校验后替换，返回空对象且不套用字段默认值），必须用 `prefault({})`（校验前替换）。
3. **服务依赖必须在 `inject` 中声明**——否则读取 `ctx.commands` 抛 `cannot get property "commands" without inject`，整个 profile 启动失败。而声明成必需依赖又会破坏 headless 组合（无命令面）。正解是**可选取值**：`export const inject = { commands: null }`（cordis 第 1058 行 `if (isNullable(config)) continue;` 即"空值 = 可选"）。注册处再用容错探测访问。

这三条都是"错误信息不指向病因"的类型，已连同依据一并写入 `README.md` 的「Writing a plugin that loads in this harness」一节。

### 第 4 轮：对话内回执

停机时向对话注入一条可见回执，使"被扣住"不再与"卡死"长得一样：

```
[peak-valley-brake] 2 message(s) are withheld because the API is priced at peak right now.
They are queued, not lost, and will be delivered automatically at 2026-09-15 04:01 UTC (2026-09-15 12:01 UTC+8).
To release them immediately, run the /peak-valley command with the argument "now".
```

关键实现选择：

1. **用 `form: 'notice'` 而非普通上下文。** 类型注释写明 notice 是"一行说明，在折叠行上展示、并提交进持久日志"——正合此用途，且 summary 受宿主 120 字符上限约束。
2. **用 `agent.inject()` 而非 `followup()`。** followup 会唤醒驱动器、然后被这个刹车自己拒绝；inject 只递交面向模型的上下文、不唤醒。
3. **每个停机窗口只投一次。** 每次唤醒都投会把安静等待变成满屏重复通知。
4. **用宿主自己的 `createUserMessage` 构造消息。** 它会铸造带 brand 的消息 id，手工拼对象做不到（第 1 轮的重建消息曾这样处理，本轮一并改正）。
5. **`llm` 声明为必需依赖，`@deepseek-ai/dsh-llm` 声明为 peerDependency。** 已用探针插件在真实宿主实测：必需依赖不会阻止加载（与 cordis 第 1058 行的空值跳过逻辑一致），`ctx.llm` 可用。`dsh-llm` 不是 `dsh-base` 的普通依赖，必须显式声明 peer 才能从 profile 解析。

**验证缺口（如实记录）**：回执的**消息形状**已对宿主类型核实、并比对了宿主内已验证可用的同类写法（`dsh-repeat-tool-reminder`），但**"渲染进真实对话界面"未能自动验证**——Web 端走 Typert RPC over WebSocket，需生成的调用描述符，无法从命令行驱动会话。该项需操作者在真实会话中确认。

### 第 5 轮：操作者可见文本改为双语

需求原文只写了"对话内提示"，未规定语言。操作者要求中文，但硬编码中文会让英文环境失效，因此做成**正规字典 + 语言解析**，而非替换字符串。

**语言解析顺序**（`locale: auto`）：
1. `$DSH_HOME/settings.yaml` 中宿主持久化的 UI 语言——**这是真正的答案**，因为它是操作者在 GUI 里实际选择的。
2. `LC_ALL`/`LC_MESSAGES`/`LANG`/`LANGUAGE` → Node 的 ICU 区域 → Windows 注册表 `HKCU\Control Panel\International\LocaleName`。这些都只是对"UI 语言"的猜测，故排在设置项之后。
3. 英文兜底。

`locale: zh|en` 可显式钉住。**日志行故意不翻译、保持英文**：它们是终端里读的诊断信息，语言稳定才便于 grep。

本轮修掉的两个真实缺陷：

1. **英文错误信息泄漏进中文句子。** 非 git 仓库时 `renderDriftReport` 把内部诊断串 `not a git repository, or git is unavailable` 直接插进中文括号里。已改为**机器可读原因码**（`no-working-directory` / `not-a-repository`），由调用方按语言渲染；并加断言确保原因码绝不进入面向模型的文本。
2. **Windows 语言名解析错误。** `Chinese (Simplified)_China` 中下划线出现在括号之后，`split(/[(_]/)[0]` 得到的是 `Chinese (Simplified)` 而非 `Chinese`，导致中文系统被判为英文。已修正切分逻辑并加断言。

**测试确定性修正**：默认 locale 解析会依赖运行机器的区域设置，使测试变得不确定。已给 `resolveLanguage` 加运行时注入点，并让所有集成测试显式传 `locale`，恢复确定性；同时**新增一条中文全链路断言**（回执 + status 输出 + 漂移提示 + 原提示词逐字保留）。

### 第 3 轮实现的手动覆盖

**为什么是斜杠命令而不是模型工具**：刹车在模型运行**之前**就拒绝了步骤，所以"模型能调用的工具"恰恰在需要时不可达。Harness 斜杠命令直接对 agent 执行、不产生模型消息、零 token 成本，是唯一在刹车生效期间仍然可用的入口。

| 调用 | 语义 |
|---|---|
| `/peak-valley`（或 `status`） | 当前档位、是否拦截及原因、下次切换时刻、本会话滞留条数、当前覆盖状态 |
| `/peak-valley now` | 放行一次；覆盖只服务**一整趟放行**，随后用尽 |
| `/peak-valley window` | 所有会话可放行，直到下一个调度边界 |
| `/peak-valley cancel` | 撤销覆盖，调度重新接管 |

三条承重性质：

1. **自行到期**：`window` 覆盖只到下一个调度边界，刹车不可能被永久关掉，且无需任何人记得重新打开。
2. **可审计**：每一次"本应被拦却放行"都会追加写入 `overrides.ndjson`——谁请求、何时授予、何时用尽、当时档位如何。写在**追加式文件**而非会话台账里，因为台账会被它所描述的那次投递本身删除。
3. **可拒绝**：`allowManualOverride: false` 时命令返回错误而非照办，运维可以用它保证任何命令都无法绕过成本策略。

覆盖状态是**进程本地、绝不持久化**的：刹车存在的意义就是它会自己重新武装，覆盖不应跨重启存活。

### 第 3 轮修掉的一个真实并发缺陷

测试暴露出：命令路径（经 `queueMicrotask` 触发放行）与定时器路径可能**并发**执行 `deliverHeld`，二者都会在对方清除台账之前读到同一批消息——结果把运维的提示词**投递两次**。`ledger.clear()` 只能保证**串行**第二次是空操作，防不住并发。

已按会话加投递串行化（`state.delivery` promise 链），并加了两条断言：重复放行趟次不得重复投递、一次性覆盖必须服务整趟放行中的所有会话（而非被第一个会话消耗）。

### 安装与验证的环境约束（第 6 轮发现，必须记录）

**同一个 `$DSH_HOME` 同时只能跑一个 harness。** `@linxin666/dsh-client-ui-task-board` 对 `$DSH_HOME/task-board/ledger-v2.lock` 加独占进程锁（记录 PID 与进程启动时刻），第二个实例会被拒绝并**整个启动失败**：

```
failed to apply loader entry ui-task-board (@linxin666/dsh-client-ui-task-board):
  task-board ledger is already owned by process 13120
```

这条约束与本插件无关，但它**直接决定本插件的安装与验证方式**，因此必须记录：

插件的安装目标是**一个 profile**，而 profile 只在启动时重新装配——所以必须重启 harness 才能加载插件。而**重启恰恰被锁阻止**（另一个实例还活着）。更进一步：**DSH Desktop 自己的 harness 跑的就是 `dsh … web`，即 `web` profile**，所以桌面应用与终端实例天然争同一把锁。这是一个极易踩中的陷阱，本次即因此产生"`dsh --profile web` 坏掉了"的现象。

两条出路（已写入 README）：

1. **重启桌面应用而不是开终端实例**——DSH Desktop 加载同一个 profile，插件会直接出现在它的界面里，不需要第二个实例。
2. **给第二个实例独立的 `DSH_HOME`**——各自持有自己的锁。代价是那份 home 有自己的 `settings.yaml`，`locale: auto` 会在那里重新推导语言。

**不要在未确认前删除锁文件**：锁是刻意的保护，两个 harness 共写同一个 task-board 账本会损坏数据。

**诊断结论的证据链**（排除本插件嫌疑）：失败条目是 `ui-task-board` 而非本插件；锁文件内容 `{"pid":13120,…}` 指向 DSH Desktop；用**该 profile 的完整真实配置**在独立 `DSH_HOME` 下启动成功，且插件自身输出 `[peak-valley-brake] 已武装；当前 峰时（提前刹车 5 分钟，延后放行 1 分钟）`——同时验证了中文渲染与峰谷判定。
